# HTPG 九类特征提取：工程入口与复现边界

本阶段把口令转换为可计算的特征。它不判断一个口令是否热门、不生成修改建议、也不执行攻击。热门/非热门应来自**频次排名及分布切点**，不是由这九项特征直接规定。之后才比较头尾的特征分布，计算信息增益率并提出建议。

依据：Xiao Yang、Jianping Zeng，*Dynamically Generate Password Policy via Zipf Distribution*，IEEE TIFS 2022，DOI [10.1109/TIFS.2022.3152357](https://doi.org/10.1109/TIFS.2022.3152357)，III-D 节的九类特征。当前是有明确口径的工程实现，不声称逐字节复现作者未公开的词典和识别器。

## 1. 现在怎么运行

Python 3.10+，特征提取只使用标准库；不需要模型、GPU、浏览器或服务器。在仓库的 `ZipfGuard` 目录运行，Windows/macOS/Linux 使用同一入口。把输入位置换成自己本机文件路径。

```sh
python -m experiments.extract_htpg_features --input "口令文件的完整路径/rockyou-withcount.txt" --lexicons resources/htpg_reference_v1.json --output local_artifacts/htpg_run_01 --write-records
```

先小规模检查可添加 `--max-lines 10000`，并使用另一个输出目录。输出目录必须不存在，程序不会覆盖旧实验。`--progress-every 500000` 控制只含数量和耗时的进度日志。

词典已随代码提供，正常提取**完全离线**。只有重新构建参考词典时才需要网络：

```sh
python analysis/prepare_htpg_lexicons.py --output local_artifacts/reference_rebuilt.json
python -m unittest discover -s tests -v
```

完成后可独立读取全部缓存、重算直方图并核对文件校验值：

```sh
python -m experiments.verify_htpg_features local_artifacts/htpg_run_01 --output local_artifacts/htpg_run_01/verification.json
```

这验证存储完整性与统计一致性，不等于已有独立人工标注来证明日期/姓氏等语义识别准确率。

输入格式是 `频次 + 一个空格或制表符 + 口令 + LF`，允许频次前有缩进。仅去掉行尾 LF 和**一个**字段分隔符，不做 `strip()`，不吞掉口令两端空格。CR 作为口令数据保留；不能把任意 CRLF 文件静默当作同一语料。频次必须是正整数；坏行立即报行号，不打印内容。

## 2. 九类特征逐一对应

设非空口令为 \(w\)，特征向量为

\[
\phi(w)=(S(w),\ell(w),U(w),D(w),K(w),P(w),B(w),E(w),N(w)).
\]

这里的向量含类别与布尔值，不是已经可以直接计算欧氏距离的九个实数。后续需要另行设计编码；不能把类别随意编号后当成有大小关系的数。

| 论文名称 / 字段 | 当前实现 | 与原文的边界 |
| --- | --- | --- |
| LSD Structure / `lsd_structure` | 按顺序记录连续字母 L、特殊字符 S、十进制数字 D 段。如论文示例 `123456!AA → D6S1L2` | 保留段顺序，不用三个总数替代；Unicode 分类是明确扩展 |
| Length / `length` | Unicode 码点数，不是 UTF-8 字节数 | 不做规范化；组合字符与预组合字符可能长度不同 |
| Capital / `capital` | 是否至少有一个大写字母 | 布尔值，不是大写字母个数 |
| Date / `date` | 完整数字段中的 1900–2099 年份；合法 YYYYMMDD、DDMMYYYY、MMDDYYYY；年月日带统一 `-`、`/`、`.` 分隔符 | 自定可验证语法；校验闰年，不识别歧义大的六位日期；原文未提供穷尽规则 |
| Keyboard / `keyboard` | US-QWERTY 相邻物理按键走查；连续至少 4 键、至少 3 种键；允许转向；大小写/Shift 归到同一按键 | 自定启发式；重复同键打断，不支持其他键盘布局；命中不等于已证明易猜 |
| Specplace / `specplace` | `none` 或按 head、middle、tail 顺序拼接的位置集合 | 原文列四种情况，但没有讲多位置冲突；本实现明确扩展为集合，如 `head+tail`，不是作者原来的四分类 |
| Lowercase / `lowercase` | 首字母是小写且第二字符不是小写，**或**末字母是小写且倒数第二字符不是小写 | 不是“含小写字母”；单个小写字符按边界孤立处理，这是显式约定 |
| WordType / `word_type` | 是否包含情感词表中的子串，不区分大小写 | 替代词典；不运行情感打分，不推断用户真实情绪 |
| Lastname / `lastname` | 是否包含姓氏词表中的子串，不区分大小写 | 替代英语语料词典，没有冒充复现作者中文姓氏列表；命中不证明是用户姓氏 |

字母采用 `str.isalpha()`，数字采用 `str.isdecimal()`，其余为 S，包括空格、标点、emoji 和组合附加符。所有位置及结构基于原字符串；仅词典匹配、键盘匹配有各自明确的大小写映射。无法严格解码为 UTF-8 的记录仍保留频次，但九项全部记 `null`（未知），不替换乱码、不猜编码、不把未知当 False。

## 3. 词典从哪来，如何避免手编结果

`resources/htpg_reference_v1.json` 内含实际词条、筛选规则、源文件 SHA-256、固定 Git 版本及许可说明。

- **情感词**：采用 [VADER 作者仓库](https://github.com/cjhutto/vaderSentiment)，固定提交 `44fc044cd877310ee8278a0eadf34bcd50d41d06`。程序选取非零情感分值、全 ASCII 字母、长度至少 3 的词条，去重后 **7,174** 项；正负情感均保留。使用词表并不等于执行完整 VADER 模型，亦不意味着该词表就是 HTPG 原始词表。MIT 许可原文保留在资源中。
- **姓氏**：采用 [FiveThirtyEight 发布的 Census 姓氏数据](https://github.com/fivethirtyeight/data/tree/4c1ff5e3aef1816ae04af63218015066e186c147/most-common-name)，固定提交 `4c1ff5e3aef1816ae04af63218015066e186c147`，筛选原始排名 1–1000、小写化，得到 **1,000** 项。该文件是其使用的 Census 2000 数据，不是 2010 数据；保留来源归属及 CC-BY-4.0 许可链接。官方 2010 下载端点本次返回拒绝页面，没有把该页面当成有效词典。

使用 Aho–Corasick 多模式匹配（一遍扫描同时查多个词），避免对每条口令循环跑数千条正则。当前是**子串匹配**：短姓氏可能误命中普通单词。这是实验口径，不是精确语义识别，下一阶段需要做词典覆盖与匹配口径敏感性分析，不能直接把命中率当作脆弱率。

若不传 `--lexicons`，WordType 和 Lastname 全部记未知；显式传入空词表或不合法结构则报错。允许用同一 JSON 格式替换更合适的词典，运行清单记录实际文件 SHA-256；不同词典的结果不能混为同一次实验。

## 4. 输出是什么，如何复用

| 文件 | 作用 |
| --- | --- |
| `features.jsonl.gz` | 可选的逐条特征缓存：源行号、非空记录序号、频次、解码状态及九项特征；没有明文或逐口令摘要 |
| `summary.json` | 程序生成的输入审计与九项特征分布；高基数特征按频次展示前 30 项，剩余合并为 other；未知单列 |
| `report.md` | 从 summary 自动生成的中文可读报告，不是人工填写结论 |
| `manifest.json` | 完成状态、输入哈希、代码哈希、词典哈希、参数、Python/Unicode 版本及各输出文件校验值 |
| `INCOMPLETE` | 运行未完成标记；成功时删除；异常或中断时留存，不能把半成品当成结果 |

`source_line` 用于回连原输入。`nonempty_index` 仅是非空记录的顺序，不擅自叫它排名；输入是否降序会审计。程序不负责合并重复字符串，种类统计要求源文件已按口令聚合。这份 Rockyou 已在前一轮独立审计中检查过重复，本提取器不伪称又做了相同检查。

`--max-lines` 输出属于前缀测试，不是随机样本；清单中的完整文件哈希只在真的读到文件末尾时填写。原始文件在读取期间如大小、修改时间或 inode 改变，任务失败，不生成有效完成清单。

逐条特征依然可通过行号和结构关联原语料，**没有明文不等于匿名**。`local_artifacts/` 和 `features.jsonl.gz` 已加入 Git 忽略；不要强制提交、不要放进公开网页。汇总也应在对外发布前审核。

## 5. 为什么有两种比例

设输入有 \(M\) 条非空记录，每条频次为 \(c_i\)，总频次 \(N=\sum_i c_i\)。对某特征 \(\phi_j\) 的取值 \(v\)，程序计算：

\[
q_j(v)=\frac{\sum_{i=1}^{M}\mathbf{1}[\phi_j(w_i)=v]}{M},\qquad
p_j(v)=\frac{\sum_{i=1}^{M}c_i\mathbf{1}[\phi_j(w_i)=v]}{N}.
\]

前者回答“多少种口令有这种特征”（前提是已聚合），后者回答“该特征覆盖多少次观测使用”。两者不能混淆。未知值也在分母内并单列，程序对每项特征校验记录数、频次之和守恒。泄露记录的计数不一定等于不同自然人的人数，因此不直接称为真实用户比例。

## 6. 本阶段之后还缺什么

下一步是在明确训练/验证/测试协议之后，用**训练部分**的频次分布得到头尾标签，再按原文计算特征的信息增益率。已经生成的全量描述统计不是独立测试结果，不能据此选择规则后又在同一份数据上宣称防护提升。逐口令建议、用户响应假设、知晓规则的离线攻击评估仍是后续阶段；本次没有接入网页，也没有替换 M1–M4 的合成实验。

验收覆盖：论文结构示例、顺序差异、边界小写、日期合法性、键盘模式、Unicode/空白、子串误命中边界、缺词典、Aho–Corasick 对照朴素搜索、频次守恒、解码未知、输出无明文、相同输入确定性、前缀与全量区分、拒绝覆盖和失败标记。
