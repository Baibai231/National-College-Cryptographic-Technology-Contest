# 02｜项目结构、确定缺陷与测量局限：代码和实测数据审计

> 审计日期：2026-09-14；主分支 `f0aa2ab`，B 系列保留分支 `24e9c09`。服务器最终分类快照读取时间：2026-09-14 22:21:33（北京时间）。本次只读检查代码、分支、实验输出与日志，不发起新的网站测试，不修改实验数据。本文不是渗透测试或完整安全审计。

## 一、结论先行

项目已经是一套可运行的**认证入口/流程分类 + 受限口令政策探测 + 数据展示协作平台**，不是只有几个脚本。但尚不能称为“稳定的大规模完整口令政策测量器”，更不是“网站整体安全性验证系统”。

最影响结论的不是小的界面问题，而是四类问题：

1. **测错对象风险**：主分支的登录任务先去找注册页面，网页和批量两条路径都有这个问题。
2. **测不到的损耗**：预检过滤、导航失败、验证门槛、找不到正确字段以及超时，层层压缩可测样本。
3. **测到了但解释过头**：前端接受不等于服务器接受；字段完整、固定置信值不等于结论正确。
4. **实验口径不够严密**：样本、入口、重复记录、不同版本、不同分支和不同阶段容易混用。

以下区分“代码确定问题”“日志观察”“需要验证的风险”“主动选择的研究边界”。不能把风险都写成已发生的事故，也不能把安全边界都写成程序 bug。

## 三、结构地图与每一层的作用

```text
目标清单 ─→ preflight_targets ─→ candidates
                                  │
                     scripts/run_measurement.py
                                  │
                登录/注册入口发现 + 页面状态导航
                                  │
             ┌────────────────────┴─────────────────────┐
             │                                          │
        流程分类与证据                         TestPassword 主动探针
             │                           候选→反馈→参数→质量门控
             └────────────────────┬─────────────────────┘
                                  │
                     JSONL 实验结果/正式 reports
                                  │
                     SQLite 展示索引 + FastAPI 网页
                                  │
                       人工核验、展示、增量同步

B 分支：application_security 的协议/强度计等模块（尚非 main 全部能力）
```

| 层 | 主要文件/目录 | 职责 | 当前结构问题 |
|---|---|---|---|
| 总入口 | `main.py` | 单站及既有测量流程 | 与批量、网页入口存在重复编排 |
| 数据集与预检 | `scripts/preflight_targets.py` | DNS、公网地址、HTTP、候选页提示 | “预检失败”混合服务不存在、阻断、HTTP 错误等多种意义 |
| 批量调度 | `scripts/run_measurement.py` | 双入口任务、并发、超时、断点恢复、落盘 | 入口意图没有可靠地传递到导航；结果需要去重 |
| 链接发现 | `utils/login_link_discovery.py` | 找注册链接/弹窗/入口 | 页面变化、共享入口、跨域身份提供方使路径复杂 |
| 页面识别 | `signup_flow_classifier/page_detector.py` | 页面和字段信号提取 | “看到提示”与“真实可交互字段”仍需严格区分 |
| 状态导航 | `navigator.py`、`classifier_engine.py` | 安全点击、状态推进、停止条件 | 可达路径搜索和最终 flow_type 混在同一复杂流程 |
| 输出分类 | `classifier.py`、`flow_types.py` | 流程类型、方法与聚合 | 标签混合认证机制、步骤顺序与测量阻断 |
| 候选与推断 | `utils/password_candidates.py`、`utils/adaptive_policy.py` | 候选构造、长度、组合与条件规则 | 搜索模型有限，模型假设未充分暴露给报告 |
| 浏览器反馈 | `utils/util_test_password.py` | 填写、事件、等待、探针、恢复 | 大文件将驱动、状态、测量、政策语义耦合 |
| 质量与覆盖 | `utils/policy_quality.py` | 完整性门控、漏斗汇总 | 以字段/结果集合判断完整，缺少属性级对照绑定 |
| 被动安全观察 | `security_observers/` | 页面可见安全信号 | 信号不是端到端安全验证 |
| 数据与界面 | `reports/`、`misc/`、`webapp/app.py` | 原始结果、人工结果、API、任务及详情 | 结果来源、缓存/新测、观察层级需更清楚 |
| 同步运维 | `webapp/server_sync.sh` 等 | 网页增量与 Git 同步 | 实验缓存与正式数据库不是同一路数据；需避免运行中版本漂移 |

规模佐证：主分支 `util_test_password.py` 约 3495 行，`webapp/app.py` 1859 行，`classifier_engine.py` 1661 行，链接发现 1606 行，页面检测 1290 行，`adaptive_policy.py` 1148 行，`main.py` 1120 行。行数说明维护耦合值得关注，**不证明算法有深度，也不单独构成缺陷**。

### 4.5 587 个预检失败到底是什么

下表按错误含义归组。原始异常前缀还包括 `gaierror` 221、`URLError` 215、`ValueError` 27、HTTP 错误 119、连接远端关闭 2、worker_error 1、直接 TimeoutError 2；不能只靠“异常文本含 dns”来分类，因为域名本身也可能含 dns。

| 归组 | 数量 | 能说明什么 / 不能说明什么 |
|---|---:|---|
| DNS 解析相关 | 222 | 包括地址不存在/无可用地址和临时解析失败；不全是地理封锁 |
| 网络不可达 | 112 | 网络栈或路由错误；可能涉及 IPv4/IPv6，不能直接确定国家原因 |
| 连接/读取超时 | 66 | 在预算内没有完成，不知道另一环境能否访问 |
| 公网地址检查拒绝 | 27 | 安全策略阻止访问非公网解析结果；需诊断 DNS，不能关闭保护强行继续 |
| TLS/证书类 | 26 | TLS 建连/校验证据不足；不是“网站没有 HTTPS” |
| 连接关闭或重置 | 11 | 网络、服务器或自动化识别均可能 |
| 连接拒绝 | 3 | 端口拒绝，不代表网站所有入口永久下线 |
| HTTP 错误响应 | 119 | 实际收到了 HTTP，说明并非根本连不上 |
| worker_error | 1 | 测量基础设施异常 |
| 合计 | 587 | 失败原因不同，不得统一解释成国内网络 |

HTTP 119 项细分：403=81，404=13，308=10，429=3，451=1，504=1，400=1，418=1，307=1，498=2，401=1，503=2，520=1，407=1。跳转状态被记录为错误的具体原因需复现该客户端的重定向处理，不能从状态码直接归因。

至少 **413+119=532** 个目标获得了 HTTP 层结果，但不保证拿到可用网页。要回答“有多少因为国内网络”，需要同目标、同时间窗、相同工具的授权多观测点对照，加上 DNS A/AAAA、连接和 TLS 分层记录。现有单观测点数据无法给出因果比例。

此外，目标清单中存在基础设施类域名的迹象；如果目标不是浏览器站点，拿它评估注册发现会稀释分母。登录基准论文选择 CrUX 用于正式网页总体，而不是无条件将所有排名域名视为可注册网站。[原文 §3.5 脚注](https://www.usenix.org/system/files/usenixsecurity23-al-roomi.pdf)

由此可定位三个损耗区间：

## 七、组员最早三个问题，解决了吗

1. **注册藏在登录页后面**：有导航工程改进，不等于通用解决。当前主分支还存在登录/注册分派缺陷；最新大量 unknown 也说明覆盖没有稳定达标。结论：部分适配，未完成跨类型可靠验收。
2. **14站第一轮通过、第二轮半数失败**：三态判定、负对照、等待、看门狗、恢复是实质进步。但目前没有同版本同样本的两轮完整复验表证明此问题解决；固定负对照、动态字段、异步反馈及模型混杂仍在。结论：有改进，稳定性未获证明。
3. **候选集和测试次序有问题**：已有自适应长度、组合、条件规则和预算，不再只有原始顺序。但候选族、控制语义、身份规则、静态上限问题依旧。结论：已重构部分策略，尚不能宣称可靠推断任意政策。

## 八、建议采用的评价指标

### 8.1 分开准确性、覆盖率、完成率

\[
\mathrm{coverage}=N_{\mathrm{conclusive}}/N_{\mathrm{eligible}},\qquad
\mathrm{precision}=TP/(TP+FP),\qquad
\mathrm{recall}=TP/(TP+FN).
\]

人工真值必须定义未知/阻断样本如何计入。对多类分类报告每类 precision/recall、macro-F1 及混淆矩阵，不只一个网页百分数。条件准确率必须同时附弃权率。

### 8.2 不只考察字段是否齐全

将推断政策 \(\hat P\) 放到不参与推断的候选集 \(T\) 上，和可靠判定器 \(O\) 比较：

\[
E_{\mathrm{pred}}=
\frac{\sum_{x\in T:O(x)\ne\bot}\mathbf1[\hat P(x)\ne O(x)]}
{|\{x\in T:O(x)\ne\bot\}|}.
\]

这个指标只验证对指定判定器和候选分布的预测，不自动变成服务端真值。再报告每条规则的可辨识状态、探针成本、失败原因和第二轮重现率。

### 8.3 对不可观测结果给界限，不伪造比例

在总样本 N 中，如果确认具有某属性的有 K 个、未知 U 个，在已确认判断都正确的前提下：

\[
K/N\le p\le(K+U)/N.
\]

这是有限样本的未知值界限，不是置信区间，也不能自动推广到全网。若分类器有误判，还要另行量化误差。当前 unknown 很多，界限很宽本身就是重要结果。

## 九、优先顺序与最低验收线（未来计划，非完成承诺）

1. **先修 A1/A2、B1/B4/B8、C1–C3**，避免继续扩大错误语义的数据。
2. 建本地有已知政策真值的表单集：至少覆盖不同事件、延迟、门控、条件长度、短口令、maxlength、iframe/重建表单；先测判定器。
3. 从本次失败类别分层随机抽样，另保留人工25个inline的完整名单。对“进不去、找不到、没启动、测不完整、测错”分开计数。
4. 相同站、相同版本和环境做两轮；候选参数不在中间针对站点逐个修改。修改后重新冻结版本。
5. 小规模达到预先设定的覆盖和错误上限后，再开千站第三阶段；避免用增加运行时长掩盖逻辑缺陷。
6. 网页优先展示证据、未知原因、是否复现与来源，不优先加未经验证的总评分。

**最终判断：工程底座值得保留，研究结论还需补证据。现阶段主要任务不是继续堆安全功能，而是把“到达—判定—推断—验证”这条链的语义和可靠性做实。**
