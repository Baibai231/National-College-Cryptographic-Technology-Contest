# 千站三阶段最终结果与项目代码结构审计

## 一、审计结论

“1000站只有2站能测口令政策”是错误解读。本次的真实结构是：**1000个输入目标→413个预检通过→31个注册密码框候选→23个复跑仍到达密码步骤→10个留下正式主动探针→6个产出长度及字符组合→2个通过当前全量完整性门控。**

更严重的问题也不只是覆盖低：部分程序状态命名与实际证据不一致，完整性门控存在可用离线反例验证的漏洞，部分属性推断混合了声明、前端观测和不成立的身份假设。因此，2个complete既不是网站可测性的上限，也不是已确认正确的政策数量。

本文以实际源码、原始JSONL、运行元数据及日志结束信息为依据。核查日期为2026-09-15；代码固定为 `f0aa2ab2a0484174a03cf806d7e774efae9ab520`。没有实施修复或新实站探测，没有改写正式 `reports/` 与 `misc/` 数据。

### 登录路径问题是代码事实，不是仅由失败率猜测

`scripts/run_measurement.py:230` 在分类分支调用 `navigate_to_signup(site)`，随后 `engine.classify(..., entry_kind=kind)`；`webapp/app.py:1243` 的实时分类也相同。标签kind可以是login，但前置导航是signup。部分站可能被后续状态机纠正，不意味着每条login都错；然而当前结果已不适合作为纯登录基准。

批量 `--measure-policy` 分支更直接：调用注册政策 `test_single_site(..., method='auto')` 后保留外层kind。第三阶段只传signup，避开了这个标签问题，但代码缺陷并未修复。

## 六、深入复核三个代表性案例

### 6.1 百度与荣耀云：complete不是完整真值

百度的8–14有实际长度二分轨迹与页面长度/组合拒绝信息，比单纯抓提示更有证据。荣耀云的上限32则由 `AdaptiveLengthPlanner` 的 `html_maxlength_hard_limit` 分支直接输出 `measured, confidence=1.0`，其最大长度没有对应主动边界轨迹。Linode的128也走此分支。

两个complete都输出p_info=True，但inline没有填写所比较的账号身份。两个p_br=False都只基于**1个符合其他政策的泄露样本被前端判为接受**。这可以作为有限的反例线索，但不能证明它们完全没有泄露口令名单，也不能确认服务端接受。

百度p_unicd/p_emoji为True、荣耀云为False，也只针对有限构造和反馈。不应据此写成所有Unicode都允许/禁止。是否破坏其他属性、输入长度单位、实际字段值变化都需检查。

### 6.2 Stripe：两套判定器与异步复验绕过

Stripe进入正式探针的唯一记录长度为1，outcome=accepted，原因是 `final-revalidation: async transient resolved: field valid at poll end`。随后 `establish_inline_control` 因要求一字符REJECTED而失败，整个政策回退。

代码 `util_test_password.py:1498` 的最终状态复验会把某些先前拒绝改为非拒绝，`:1560`附近再映射成ACCEPTED；这条分支不像无反馈分支那样要求已建立负对照。**它说明接受证据不统一，并不说明Stripe真的允许一字符密码。**

### 6.3 ipinfo：180次全拒绝，不是网站政策本身的结论

所有拒绝都来自字段class路径，记录的native validity却为True。错误类只保存前50字符，未包含触发正则的完整token，无法仅凭现有证据确定哪个class造成了拒绝。

代码使用 `\b(error|invalid|danger)\b` 匹配class字符串。静态存在的CSS工具类（例如 `invalid:border-red-500`）也会匹配，但不表示对应伪类当前生效。这是**可复现的检测器风险**；它是否就是ipinfo的实际根因仍需保存完整匹配token或DOM证据后确认。不能将推测写成已定位的网站事实。

更确定的是180条同源拒绝没有触发诊断退出，最终外层900秒终止，说明仅增大超时不能解决这类问题。

## 七、项目结构、已有作用与缺陷

```text
目标集/预检 → 批量调度或网页入口
                    ↓
         链接发现 → 状态/视图导航 → 流程分类
                    ↓
      inline预检 → TestPassword → 自适应政策推断
                    ↓
              质量门控/证据输出
                    ↓
        实验缓存 ≠ 正式reports → SQLite展示索引
                                      ↓
                               人工核验与增量同步
```

| 模块 | 主要源码 | 职责与问题 |
|---|---|---|
| 目标与预检 | `scripts/build_target_corpus.py`、`preflight_targets.py`、`utils/static_auth_discovery.py` | 公网访问和提示排序；通过预检不等于认证候选，HTTP失败混合网络/页面状态 |
| 批量编排 | `scripts/run_measurement.py` | 并发、看门狗、检查点、落盘；kind和实际导航不一致 |
| 单站编排 | `main.py` | 分类→字段定位→inline预检→政策→回退；多个提前返回缺一致诊断字段 |
| 入口发现 | `utils/login_link_discovery.py`、`signup_candidates.py` | 关键词、候选排名、共享入口和frame发现；启发式需要独立真值评测 |
| 页面与路径 | `signup_flow_classifier/page_detector.py`、`navigator.py`、`classifier_engine.py` | 状态、视图与安全动作；搜索失败、测量阻断和认证事实需要分轴 |
| 浏览器故障 | `signup_flow_classifier/browser_failures.py` | 故障归一与恢复；本批仍4个WebDriver120秒超时 |
| 反馈判定 | `main._detect_method`、`utils/util_test_password.py` | 存在预检与正式检测两套规则，事件和证据难以保持一致 |
| 策略与候选 | `utils/password_candidates.py`、`adaptive_policy.py` | 有二分、组合、条件探针；依赖固定模型、构造和单调性 |
| 质量控制 | `utils/policy_quality.py` | 字段/类型门控，尚缺属性级实验闭环；漏斗计数可被标签误导 |
| 安全观察 | `security_observers/` | 页面能力与局部元数据；加权评分不等于安全证明 |
| 数据/界面 | `reports/`、`misc/`、`webapp/app.py` | 正式结果、人工核验、缓存/重测、异步任务；来源与证据层级需显式展示 |
| 同步 | `webapp/server_sync.sh` | 6小时同步网页增量；不会自动把实验.cache全部变成正式网页结果 |
| B系列 | 独立分支 `application_security/` | 有协议/强度计/证据模型代码，不是main全部已集成能力 |

`util_test_password.py`约3495行，`webapp/app.py`1859行，分类引擎1661行、入口发现1606行、页面检测1290行。行数不等于缺陷，但浏览器、状态、策略、日志和异常耦合在大文件，导致修一个站容易影响其他阶段。

## 八、按优先级列出具体问题与验证办法

### P0：会改变结论含义的问题

| P0-1 | 批量和网页分类均先注册导航 | 登录统计可能测错对象 | 两入口分派、共享入口守卫、实际表单角色回归 |

### P2：维护与展示上的改进

网页的统计、分类政策和实测政策应持续分开；实验.cache不能被悄悄导入正式结果。详情页应显示本次/历史、代码版本、观察层级、每项的未知原因、是否人工复核，而不是仅给总分或complete。

主分支评分代码会给可见OAuth state/PKCE或Passkey信号打启发式分，并对未知项排除分母。它同时有coverage和边界提示，这是优点；但若前端突出高分而弱化低覆盖，就容易误导。CPAM层级是项目定义，不是通用认证等级标准。

依赖和浏览器/驱动版本需要固定；独立代码快照只固定源码，不固定共享venv与浏览器更新。网页同步和研究运行应分离。异步任务、重测、取消、落盘和重启恢复宜有明确状态机，而非多个入口分别编排。

## 十、历史303站与人工inline观察如何使用

历史文件 `reports/archive/policy_coverage_baseline_20260911.json` 是303个signup主机：61个记录密码框，16个主动测量，5个complete（1.65%）。不能与本批1000目标的2/1000直接对比性能升降，因为样本、入口和条件不同，而且旧门控也存在上述口径问题。

## 十一、还缺哪些不能由访客模式补出的结论

默认不提交、不登录的测量无法证明：服务端真实政策与前端一致；口令存储哈希与盐合规；断言/令牌被正确验证；MFA强制；恢复不可降级；登录限速；账号可枚举；所有入口都安全。点击到一个协议或看到一个安全按钮都不等于验证了这些性质。

合理划界不是缺点，而是研究可信度的一部分。可采用本地真值环境和小规模授权账号子样本验证机制，再明确对真实访客观测可外推到哪一步。

## 十二、接下来按什么顺序修与验证

1. 修入口分派、控制绑定、静态/主动证据和身份项，避免继续积累语义有误的数据。
2. 统一反馈判定器，保存前置探针，增加重复同源拒绝止损；优先复现Stripe/ipinfo类案例。
3. 政策分“核心长度/组合”“扩展允许项”“服务端确认”，每项支持未知/不可测，不为提高complete放宽真值要求。
4. 本地已知规则表单做事件、延迟、工具类、整表门控、iframe重建、条件长度和Unicode单位测试。
5. 固定样本和版本做同站两轮，不在中间逐站打补丁；报告覆盖、误判、弃权、耗时和预测误差。
6. 完成上述验收后，再扩大目标规模。正式数据更新要保留旧结果、来源和审核步骤。

数学上，建议分别报告：

\[
C=N_{conclusive}/N_{eligible},\qquad
E=\frac{\#\{\hat P(x)\ne O_{truth}(x)\}}{N_{paired}},\qquad
R=\frac{N_{two\ runs\ consistent}}{N_{paired\ sites}}.
\]

各分母、弃权处理和真值来源必须写明。31→2是完成率，不是上述误差或准确率。若N个站中K个确认有属性、U个未知，在已确认判断正确的前提下只有 \(K/N\le p\le(K+U)/N\) 的有限样本界限，不是全网置信区间。
